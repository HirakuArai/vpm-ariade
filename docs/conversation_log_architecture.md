# 会話ログアーキテクチャ

## 現状の構造

### 1. 全体会話ログ (`conversations/`)
```
conversations/
├── conversation_20250621.json
├── conversation_20250622.json
└── conversation_20250623.json
```

**特徴**:
- 日付ごとに全会話を記録
- プロジェクトを問わずすべての会話が含まれる
- Git自動コミット・プッシュ対象
- 監査証跡として重要

### 2. プロジェクト固有ログ (`data/conversations/{project_id}/`)
```
data/conversations/
├── proj-20250618-075700-122/
│   ├── 20250621.jsonl
│   ├── 20250622.jsonl
│   └── 20250623.jsonl
└── proj-20250611-154246-996/
    └── 20250611.jsonl
```

**特徴**:
- プロジェクトごとに分離
- JSONL形式（1行1メッセージ）
- 再分析機能で使用
- プロジェクト関連の会話のみ

## 問題点

1. **重複管理**: 同じ会話が2箇所に保存される
2. **整合性**: 全体ログとプロジェクトログの同期が必要
3. **ストレージ**: 容量の無駄遣い
4. **複雑性**: 2つのシステムの維持が必要

## 推奨される改善案

### Option 1: 統一管理（推奨）
```
data/conversations/
├── global/
│   ├── 20250621.json  # 全体ログ（Git管理）
│   └── 20250622.json
└── projects/
    ├── proj-20250618-075700-122/
    │   ├── 20250621.jsonl
    │   └── 20250622.jsonl
    └── proj-20250611-154246-996/
        └── 20250611.jsonl
```

### Option 2: インデックス方式
- 全体ログのみを保存
- プロジェクトごとにインデックスファイルを作成
- 必要時に全体ログから抽出

### Option 3: タグ方式
- 各メッセージにプロジェクトIDをタグ付け
- 単一のログファイルで管理
- フィルタリングで対象会話を抽出

## 移行戦略

1. **Phase 1**: 現状維持（両方のログを継続）
2. **Phase 2**: 新規会話は統一形式で保存
3. **Phase 3**: 既存ログの移行ツール実行
4. **Phase 4**: 旧形式の廃止

## 当面の対応

- `conversation_migrator.py` を使用して必要に応じて移行
- 新規プロジェクトは両方のログに記録
- 再分析はプロジェクト固有ログを優先使用
